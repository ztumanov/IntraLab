# Архитектура платформы InfraLab

## 1. Обзор системы
**InfraLab** — платформа управления Linux-инфраструктурой, сетями, контейнерами и приложениями. Архитектура спроектирована модульно, чтобы каждый этап развития (Server Inventory → SSH & Host Telemetry → Docker → Network Topology → Deployments → Alerting) опирался на строгий контракт API и безопасное хранилище секретов.

```
+-------------------------------------------------------------------+
|                   Frontend SPA (React + TypeScript)               |
|  - DashboardPage / ServersPage / ServerDetailsPage                |
|  - TanStack Query (кэширование, инвалидация, оптимистичные апдейты)|
+---------------------------------+---------------------------------+
                                  | REST API (/api/*) + Bearer Token
                                  v
+-------------------------------------------------------------------+
|               Backend API Layer (Go / Node Runtime)               |
|  - Валидация входных данных (IP, FQDN, порт 1..65535, SSH-ключи)  |
|  - Менеджер секретов AES-256-GCM (шифрование паролей и ключей)    |
|  - SSH Connector (рукопожатие, проверка статуса, сбор метрик ОС)  |
+----------------+----------------------------------+---------------+
                 | SQL (Drizzle / pgx)              | SSH (TCP :22)
                 v                                  v
+--------------------------------+  +-------------------------------+
|     PostgreSQL 16 Database     |  |    Target Linux Hosts         |
|  - users (RBAC / владельцы)    |  |  - uname -sr / /etc/os-release|
|  - servers (инвентарь + шифры) |  |  - nproc / free -m / uptime   |
+--------------------------------+  +-------------------------------+
```

## 2. Этап 1 & Этап 2: Инвентаризация и SSH-подключение

### Безопасное хранение учётных данных (AES-256-GCM)
1. Пользователь может выбрать метод аутентификации для каждого Linux-сервера:
   - **`password`** — парольная аутентификация SSH;
   - **`private_key`** — аутентификация по приватному ключу OpenSSH / PEM (`Ed25519`, `RSA`).
2. Перед записью в колонку `encrypted_secret` таблицы `servers` секрет шифруется алгоритмом **AES-256-GCM** со случайным 96-битным вектором инициализации (`IV`) и тегом аутентификации (`AuthTag`).
3. API никогда не возвращает `encrypted_secret` или открытый пароль/ключ клиенту — фронтенд получает только булев флаг `has_secret: true | false` и тип `auth_type`.

### Проверка доступности и сбор телеметрии (`POST /api/servers/:id/check`)
При вызове эндпоинта проверки (или автоматически при создании сервера с флагом `verify_now: true`):
1. Бэкенд расшифровывает секрет в оперативной памяти и открывает SSH-сессию к `ip_address:ssh_port`.
2. Измеряется задержка рукопожатия (`latency_ms`).
3. При успешной авторизации выполняется неинтерактивный сбор базовых фактов о хосте:
   - Версия ядра (`uname -sr`);
   - Дистрибутив ОС (`/etc/os-release`);
   - Количество ядер CPU (`nproc`);
   - Объём оперативной памяти (`free -m`);
   - Время непрерывной работы (`uptime -p`).
4. Статус сервера переводится в **`ONLINE`**, а собранные метрики сохраняются в PostgreSQL.
5. При ошибке сети или авторизации статус переводится в **`OFFLINE`**, а точная причина (`Connection refused`, `Connection timed out`, `Permission denied`) записывается в `last_check_error`.
